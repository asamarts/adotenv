## Required evidence before tagging 1.0

1. Run the complete release gate:
   ```console
   cargo fmt --all --check
   cargo test --workspace --all-features --locked
   cargo clippy --workspace --all-targets --locked -- -D warnings
   cargo +1.81 build -p adotenv-cli --locked
   RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked
   python3 conformance/check_adotenv.py --setup
   cargo package -p adotenv --locked
   ```
2. Record a fresh idle-host benchmark run and compare representative midpoints
   with [performance.md](performance.md). Repeat 1.5x–2x deviations and block
   above 2x until explained.
3. Confirm the weekly fuzz workflow has accumulated the sustained period chosen
   for 1.0, with no unresolved crash or sanitizer finding. Preserve reproducers
   and minimize any failure before closing it.
4. Confirm all five crates have matching versions, the tag matches every package,
   and a forced patch-semver check reports no accidental API break.
5. Verify the external-user requirement with a real adopter, a documented
   migration problem and a successful integration. A name or link may be kept
   private if the user prefers, but the evidence must be real.
6. Verify crates.io, docs.rs and the GitHub Release after publication. Do not
   move a tag after an upload succeeds.

## Deferred work and accepted limitations

- `config` remains at 0.14 because 0.15 changes key-normalization behavior and
  the current 0.15 line requires Rust 1.88/edition 2024.
- Windows writes use a best-effort backup swap; they are not crash-atomic.
- No language server, semantic tokens or WebAssembly playground is part of 1.0.
- The temporary `CARGO_REGISTRY_TOKEN` break-glass secret should be rotated on
  the normal credential schedule; Trusted Publishing handles normal releases.
