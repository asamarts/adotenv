## Required evidence before tagging 1.0

1. Run the complete release gate:
   ```console
   cargo fmt --all --check
   cargo test --workspace --all-features --locked
   cargo clippy --workspace --all-targets --locked -- -D warnings
   cargo +1.81 build -p adotenv-cli --locked
   RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked
   python3 conformance/check_adotenv.py --setup
   cargo package -p adotenv --locked
   ```
2. Record a fresh idle-host benchmark run and compare representative midpoints
   with [performance.md](performance.md). Repeat 1.5x–2x deviations and block
   above 2x until explained.
3. Confirm four consecutive scheduled weekly fuzz runs for all five targets
   after the last fuzz-relevant change, with no crash or sanitizer finding.
   The 300-second jobs must all succeed; manual dispatches do not count toward
   the four scheduled runs. Preserve reproducers and minimize any failure
   before closing it.
4. Confirm all five crates have matching versions, the tag matches every package,
   and run the forced patch-semver check:
   ```console
   cargo semver-checks check-release --baseline-version 0.9.17 --release-type patch --features load,serde
   ```
5. Verify the external-user requirement with a real adopter: a public or private
   project outside this repository using a published adotenv crate, maintainer
   confirmation, the version and features used, and a documented integration or
   migration note. A name or link may be kept private if the user prefers, but
   the maintainer confirmation must be recorded. Public package downloads or
   issue comments alone do not satisfy this criterion.
6. Verify crates.io, docs.rs and the GitHub Release after publication. Do not
   move a tag after an upload succeeds.

## Sustained-period definition

Four consecutive **scheduled** weekly Fuzz runs for every target (`parser`,
`edits`, `encoding`, `resolve`, `format`) must complete successfully after the
last change that touches core parsing, edits, encoding, resolution or formatting.
A manual dispatch, cancelled run, skipped target or failed job does not count.
The weekly workflow's 10-minute job timeout and 300-second engine limit apply.

When the fourth run passes, record its run IDs and dates here and update the
status to Complete. If a fuzz-relevant change lands afterward, the count
restarts.

## External-user definition

A qualifying adopter is a project outside this repository that depends on a
published `adotenv` crate (core or companion) and has integrated it. Record:

- project name or a private-maintainer confirmation;
- crate and version used, plus enabled features;
- whether the integration uses parsing, loading, CLI, process mutation or an
  adapter;
- one real integration or migration finding, even if minor; and
- permission/preference for public attribution.

Downloads, issue reactions and internal examples do not count. The evidence may
be kept private, but it must be real and recorded in this checklist.
